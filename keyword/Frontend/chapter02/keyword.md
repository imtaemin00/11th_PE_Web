- React 컴포넌트와 JSX
    - JSX는 HTML과 어떤 점이 다르며 React 컴포넌트 안에서 어떤 역할을 하나요?

  JSX

  JavaScript 안에서 HTML과 비슷한 모양으로 UI를 작성할 수 있게 해 주는 JavaScript 문법 확장이다

  **HTML과의 차이**

  |  | HTML | JSX |
      | --- | --- | --- |
  | 정체 | 브라우저가 바로 읽는 마크업 언어 | JavaScript 문법 확장. 브라우저가 바로 읽지 못함 |
  | 동작 | 그대로 화면 구조가 됨 | 빌드 도구(Vite)가 JavaScript 함수 호출로 변환한 뒤 React가 사용 |
  | 클래스 | class | className |
  | 값넣기 | 정적인 글자만 | {}안에 변수, 계산식, 함수 호출 결과 |
  | 태그 | <img>처럼 안닫아도 됨 | <img/>처럼 모든 태그를 닫아야 함 |

  **React 컴포넌트 안에서의 역할**

  React - UI를 만들고 갱신하는 라이브러리
  JSX = 그 UI의 모양을 읽기 쉽게 작성하는 문법

  컴포넌트는 JSX를 반환하는 함수이고, 이 JSX는 "현재 데이터일 때 화면이 어떤 모습이어야 하는지"에 대한 설명이다. React는 이 설명을 읽어 실제 브라우저 화면을 만든다.

    - 하나의 화면을 여러 컴포넌트로 나누면 어떤 장점이 있으며, 분리 기준은 어떻게 정할 수 있을까요?

  장점

    - 재사용: 같은 UI를 여러 번 쓸 수 있다 (MovieCard 하나로 영화 여러 편 표시)
    - 가독성: 한 파일이 짧아지고 역할이 이름으로 드러난다
    - 유지보수: 카드 모양을 바꿀 때 MovieCard만 고치면 된다

  분리 기준

    - 반복해서 쓰는 UI (영화 카드)
    - 역할이 분명한 UI (헤더, 페이지네이션)
    - 코드가 길어져 따로 읽고 싶은 부분

    - 조건부 렌더링과 목록 렌더링은 데이터에 따라 보여 줄 컴포넌트를 어떻게 결정하나요?

  **조건부 렌더링**

  조건의 참/거짓에 따라 다른 JSX를 반환한다.

    ```jsx
    {movies.length === 0 ? <p>표시할 영화가 없어요.</p> : <ul>...</ul>}
    ```

  **목록 렌더링**

  map() 으로 배열의 각 데이터를 JSX 요소로 바꾼다. 데이터 개수만큼 UI가 만들어지고, 각 항목에는 구분용 key를 붙인다.

    ```jsx
    {movies.map((movie) => <li key={movie.id}>{movie.title}</li>)}
    ```

  즉 화면을 직접 바꾸는 게 아니라, 데이터를 보고 "지금 보여 줄 모습"을 계산해서 반환한다

- props와 단방향 데이터 흐름
    - 부모와 자식 컴포넌트 사이에서 props는 어떤 역할을 하나요?

  props - 부모가 자식에게 전달하는 입력값
  함수의 매개변수처럼, 같은 컴포넌트라도 받은 props에 따라 다른 화면을 만든다.

    ```jsx
    // 부모
    <MovieCard title="오디세이" releaseDate="2026.08.05" isBookmarked={false} />
    
    // 자식
    function MovieCard({ title, releaseDate, isBookmarked }: MovieCardProps) { ... }
    ```

  전달한 값들은 하나의 객체로 묶여 자식에게 전달되고, 자식은 구조 분해 할당으로 필요한 값을 꺼내 쓴다. 같은 MovieCard라도 받은 props가 다르면 다른 화면을 만든다

    - 데이터가 부모에서 자식으로만 흐르면 화면의 변화를 추적하는 데 어떤 도움이 되나요?

  데이터가 한 방향으로만 흐르면 값의 출처가 항상 위쪽 한 곳이다

  화면에 잘못된 제목이 보이면 → MovieCard가 받은 props 확인 → 그 props를 넘긴 부모 확인 → 부모의 상태 확인. 이렇게 위로만 따라가면 원인을 찾을 수 있다

  만약 자식도 값을 마음대로 바꿀 수 있다면, 여러 컴포넌트 중 누가 언제 바꿨는지 모두 뒤져야 한다.  하지만 단방향 흐름에서는 값을 바꿀 수 있는 곳이 부모 하나라서, 변경 원인을 찾을 곳이 정해져 있다

    - props에 TypeScript 타입을 붙이면 컴포넌트를 잘못 사용하는 실수를 어떻게 찾을 수 있나요?

    ```jsx
    interface MovieCardProps {
      title: string;
      releaseDate: string;
      isBookmarked: boolean;
    }
    ```

  이 약속과 다르게 쓰면 브라우저에서 실행하기 전에 에디터와 pnpm build 단계에서 오류를 알려 준다.

    - 필요한 값을 빠뜨림
    - 타입이 다름
    - 이름 오타

  타입이 없으면 이런 실수가 화면에 undefined로 나오거나 아예 안 나오는 식으로 조용히 드러나서 원인을 찾기 어렵다

- 상태와 리렌더링
    - 일반 변수와 state(상태)는 값이 바뀐 뒤 화면을 다시 보여 주는 방식이 어떻게 다른가요?

  일반 변수 - 바꿔도 React가 몰라서 화면이 안 바뀌고, 다시 실행되면 초기값으로 돌아간다

  state - React가 값을 따로 보관해 유지하고, set 함수를 호출하면 리렌더링을 요청해 달라진 부분만 화면에 반영한다

    - React에서 원본 상태를 직접 수정하지 않고 새로운 값으로 업데이트해야 하는 이유는 무엇일까요?

    1.  React가 변화를 알아채는 방법 때문
        React는 새 상태가 이전 상태와 같은 값(같은 참조)인지 비교해서 리렌더링 여부를 정한다. 배열·객체는 내용이 아니라 "메모리 위치"로 비교한다.

    ```jsx
    movies.push(newMovie);
    setMovies(movies);
    ```

  이처럼 같은 배열에 내용을 추가해도 이전과 여전히 같은 배열이라 React가 변화를 놓칠 수 있다

  2.이전 상태를 보존하기 위해

  원본을 고치면 이전 값이 사라진다. 새 값을 만들면 이전 값과 다음 값을 비교하거나 되돌리기 쉽다

    3. 다른 곳에 영향을 주지 않기 위해

  같은 객체를 여러 컴포넌트가 참조하고 있을 수 있어서, 한쪽에서 직접 고치면 예상치 못한 곳이 같이 바뀐다.

    - 이전 상태로 다음 상태를 계산할 때 업데이터 함수를 사용하는 이유는 무엇일까요?

  state는 그 렌더링 시점의 값으로 고정돼 있어서, 한 번에 여러 번 업데이트하면 옛날 값을 반복해서 쓴다.

    ```jsx
    setCount(count + 1);  
    setCount(count + 1);  
    setCount(count + 1); 
    ```

  따라서,  세 줄 모두 같은 렌더링의 count(0)를 보고 계산해서 1이 된다.

    ```jsx
    setCount((current) => current + 1);  
    setCount((current) => current + 1); 
    setCount((current) => current + 1);
    ```

  업데이터 함수는 React가 바로 앞 업데이트까지 반영된 최신 값을 current로 넘겨주기 때문에 순서대로 정확히 계산된다.

- 상태 공유와 Context
    - 여러 컴포넌트가 같은 상태를 사용해야 할 때 상태를 어느 컴포넌트에 두는 것이 좋을까요?

  그 컴포넌트들의 가장 가까운 공통 부모에 둔다 = (상태 끌어올리기)

  부모가 상태와 변경 함수를 가지고 자식에게 props로 내려준다.
  북마크 상태를 카드마다 두지 않고 목록을 가진 부모가 관리하는 식이다.

  MovieCard마다 따로 상태를 두면
  카드마다 북마크 정보가 흩어져서, 전체 중 북마크된 영화가 몇 개인지 알 수 없다

    - props 전달, 상태 끌어올리기와 Context는 각각 어떤 상황에 알맞을까요?

  props: 가까운 부모-자식, 한두 단계 전달
  값이 어디서 왔는지 코드에 그대로 보여서 가장 명확하다

  상태 끌어올리기: 형제 컴포넌트가 같은 데이터를 보여 주고 바꿔야 할 때

  Context: 테마, 로그인 사용자처럼 멀리 떨어진 여러 컴포넌트가 같은 값을 쓸 때 (중간 컴포넌트가 안 쓰는 props를 계속 넘기는 props drilling 방지)

  기본은 props, 필요할 때 끌어올리기, 너무 깊어지면 Context 순서로 고려한다.

    - 모든 값을 Context로 전달하면 어떤 문제가 생길 수 있을까요?
    1. Context 값이 바뀌면 그 값을 읽는 모든 컴포넌트가 리렌더링된다
    2. 값이 어디서 왔는지 코드에 드러나지 않아 추적이 어렵다
    3. 특정 Context가 있어야만 동작해서 컴포넌트 재사용이 어렵다
